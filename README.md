# EvoTau

EvoTau is a local research layer for policy-preserving customer–service co-evolution on a pinned tau-bench Retail text runtime. τ-bench remains responsible for environment state, tools, simulation, and evaluation; EvoTau adds bounded strategy search, failure attribution, repair gates, replay archive, and manifest-bound checkpoints.

## Local setup

Run these commands from the EvoTau directory on macOS/Linux:

    python3.12 -m venv .venv
    source .venv/bin/activate
    python -m pip install -e ".[dev]"
    python -m pytest -q -p no:cacheprovider
    python -m evotau.phase0 --config configs/mvp.yaml
    python -m evotau.mechanism_preflight --config configs/phase3-mechanism.yaml

The pinned upstream dependency is optional because the offline protocol tests do not need tau-bench or model credentials. To install the audited upstream revision for integration work:

    python -m pip install -e ".[tau-bench]"

The upstream pin is sierra-research/tau2-bench commit b7ea9074c1cba482b30687fecdb5c8425fd6f619, package version 1.0.1.

## Phase 0

The Phase 0 manifest record is saved at experiments/manifests/evotau-phase0-retail-smoke.json. It selects Retail train task 73 for evolution and task 93 for validation, with heldout empty and tasks 46 and 47 excluded. It sets evaluation_type to all, max_steps to 64, one episode, concurrency one, zero provider retries, and a maximum of 70 provider attempts. The manifest records the EvoTau Git commit, whether the worktree was clean, an EvoTau source snapshot hash, and the pinned τ-bench source fingerprints. The exact task and split file fingerprints are in configs/mvp.yaml.

By default, real_provider_enabled is false and model IDs are unset. The preflight command validates manifest invariants without calling a model. If exact upstream task and split files are available locally, pass both to the preflight command using --tasks-json and --split-json; their Git blob fingerprints are checked before eligibility validation.

The optional runtime entry points are in `src/evotau/tau_adapter.py`. `run_phase0_episode` and `evotau-phase0-run` refuse to run unless the manifest explicitly enables the real provider and freezes all four role model IDs (agent, customer, reviewer, and NL evaluator) plus each role's sampling arguments. The supported frozen sampling keys are `temperature`, `top_p`, `max_tokens`, `frequency_penalty`, and `presence_penalty`; defaults set temperature to zero. The CLI verifies every manifest source fingerprint, task eligibility, and output-path uniqueness before dispatch. It uses τ-bench `run_simulation` with `EvaluationType.ALL`, then invokes the native full conversation reviewer; evaluator and reviewer calls share the same hard budget. EvoTau injects the frozen evaluator and reviewer settings into τ-bench's imported judge functions so no upstream default model is used implicitly. Provider response caching and retries must be disabled. The runner saves the manifest, native simulation trajectory, review, actual completion-attempt and cache-hit counters, reported prompt/completion tokens, and hashes of the rendered agent/customer prompts. If token usage is absent, the result records that count as unavailable. If review fails after simulation, the trajectory and a budgeted incomplete-run record are retained. Offline tests and preflight make no real provider requests; installation is needed only for the optional upstream integration test.

To execute the single live Phase 0 episode, first make a separate config copy with all four model IDs and their `model_args` frozen, `real_provider_enabled: true`, and a new `output_path`. Then invoke `python -m evotau.phase0_run --config path/to/frozen-live-config.yaml --tau2-data-dir /path/to/pinned-tau2/data`. The checked-in MVP config intentionally remains provider-disabled.

The pinned native Retail environment and `Orchestrator` construction, including both prompt adapters, have been verified without provider calls. To repeat that integration check after installing the optional extra, set `EVOTAU_TAU2_DATA_DIR` to the `data` directory from the pinned checkout and run:

    EVOTAU_TAU2_DATA_DIR=/path/to/tau2-bench/data python -m pytest -q -k pinned_tau_runtime

The native integration checks verify all 19 pinned τ-bench source fingerprints, load the Retail tasks, construct the native environment and `Orchestrator`, check both prompt adapters, and run the actual `run_simulation`/`EvaluationType.ALL`/reviewer path using deterministic local completions. A further offline integration test carries the Phase 0 result into a complete two-generation native Phase 3 controller run and checks the shared budget and checkpoint context. These tests make no provider calls and produce no research evidence. The provider-backed Phase 0 exit remains pending because the checked-in manifest disables provider use and has no frozen model IDs.

## Phases 1–3 mechanism layer

The provider-agnostic research protocol is implemented in `src/evotau`: immutable episode/failure records, explicit independent failure promotion, deterministic one-axis Customer mutation, paired strict selection, an append-only SQLite archive of verified failures and strategy snapshots, structured policy-referenced Service repairs, target/history/clean/validation gates, atomic manifest-bound per-episode checkpoints, and a two-generation Customer-first controller. A one-episode failure signal is provisional: fitness, repair, and archive use require independent audits of both the source and a fresh-seed rerun of the same task under the same Customer and Service strategies, with the exact same policy signature. Existing fresh confirmation runs serve as this rerun; unreproduced signals remain diagnostics, and confirmation episodes are not double-counted as additional discoveries. Each `RepairProposal` carries a falsifiable verification hypothesis; its `GateReport` preserves the audited proposal, evaluated candidate, frozen initial S0 checkpoint ID, and per-clean-unit S0 episode references even when rejected. Clean gates require matching native-Customer episodes for the incumbent, candidate, and initial S0 checkpoint; candidate success must preserve both incumbent-passing tasks and every initial-S0 success anchor. The controller accepts an `EpisodeRunner`; it does not create model clients or supply task truth. A Service strategy can change only when a returned `GateReport` accepts that exact candidate. Phase 3 also freezes three MVP failure classes and their exact Retail policy references—missing identity verification, missing explicit confirmation before a write, and incomplete write scope—into its hashed manifest; out-of-scope signatures or policy references cannot enter fitness or the replay archive.

The native Phase 3 path now uses the manifest-bound `evolver` model to rank the existing legal Customer mutation operators. The Evolver receives only E-panel failure IDs and fixed failure signatures, never task IDs, transcripts, or V/H observations; it returns operator names, while EvoTau constructs the actual strategies through the deterministic one-axis mutation code. Its request uses the shared provider budget, and the generation record stores a hash of the exact sanitized proposal context. Callers can inject an alternate selector for offline testing or a preregistered control.

Independent episode audits separately record factual Customer validity, whether an EvoTau behavior had an opportunity to apply, adherence when applicable, and the count of invalid repeated write calls. `None` can run the native τ-bench Customer without a strategy overlay; Service clean-gate pairs require that mode, while adversarial target/history/validation pairs must have an applicable, adherent Customer strategy. A Service gate fails closed when repeated-write audit counts are missing or the candidate adds one. Cross-play reports the count and audit coverage so unknown observations stay visible; attribution rates use applicable, adherent episodes as their denominator.

Customer mutation records now include exact changed fields, the expected behavioral effect, and the failure IDs that support a failure-conditioned proposal. `FailureArchive.active_representatives()` caps replay representatives at 32, orders them deterministically by recent recurrence, severity, replay coverage, and recency, and retains the full append-only history. `mark_replayed()` and `active_replay_coverage()` report representative coverage; each generation checkpoint stores the resulting coverage snapshot with its decision. `evotau.calibration.calibrate_attribution()` reports whether independent double review of at least 30 distinct candidate positives meets the plan's 90% conservative precision and 10% critical-fact dispute thresholds. It returns `insufficient_evidence` or `pause_automation` when the corresponding condition is not met; it does not generate human reviews.

After collecting two independent human judgments per proposed failure, save them in the strict version 1 JSON format (`schema_version` and `cases`; each case contains distinct anonymized reviewer IDs, reviewer refs/verdicts, and `critical_fact_dispute`) and run `evotau-calibrate-attribution --input path/to/reviews.json`. The report includes a SHA-256 of the exact input artifact.

Offline mechanism fixtures cover no-change generations, invalid/unverified attribution, repair rejection, replay deduplication, episode and decision recovery, manifest-bound strategy IDs, exact-signature failure reproduction, and fresh-seed Customer confirmation. Each atomic generation checkpoint now retains the candidate evaluations, confirmation panel, selection decision, verified failures with source/reproduction audit references, Service gate outcome, and idempotent archive writes. A prepared-but-uncommitted generation is resumed from that saved decision, so it does not ask the ServiceTransition to regenerate a decision after a crash. `build_crossplay_matrix` summarizes balanced frozen Customer × Service runs, keeps invalid/uncertain/infrastructure episodes visible, and counts only independently audited, strategy-reproduced failures. These checks establish software behavior only; they do not establish a research result. `configs/phase3-mechanism.yaml` freezes the E/V tasks, upstream source fingerprints, strategy hashes, K=2, two generations, 23-episode/1,800-attempt ceilings, and provider-disabled default. The preflight validates task eligibility against the exact pinned task and split blobs when those files are supplied.

For a future multi-task pilot, `evotau.eligibility.validate_generalization_selection()` checks train-only E/V, official-test H, ex-ante task eligibility, and disjoint extracted customer/order/entity identifiers. It rejects an unsafe requested partition rather than silently filtering tasks. Its ID-based screen does not prove policy/tool compatibility or task satisfiability; those require a recorded semantic task review before a run.

`evotau.research_analysis.analyze_adaptation_response()` checks the four cross-play rates for a proposed Service repair and subsequent Customer response. It requires a confirmation matrix on the same frozen tasks and strategy IDs with disjoint episode seeds, returns `observed`, `not_observed`, or `inconclusive`, and records hashes for both matrices. This is a descriptive arms-race check, not a significance test.

`analyze_rq3_longitudinal_response()` aggregates consecutive confirmed response chains across independent evolution-seed blocks and compares adaptive co-evolution with frozen-Service and budget-matched random-mutation controls. It validates fixed task/seed schedules, strategy lineage, fresh confirmation panels, paired budgets, and the frozen-Service invariant. Each transition input retains both cross-play matrices; loading recomputes the four-cell response summary and rejects a mismatch, while the report's percentile interval resamples seed blocks only. With fewer than three blocks it reports insufficient runs. Use `evotau-analyze-rq3 --input rq3-runs.json --output rq3-report.json` for the strict version 2 JSON format. The report records the exact input SHA-256, and the CLI never overwrites an existing output. Results remain descriptive until pilot-informed sample size and formal hypotheses are preregistered.

`evotau-calculate-power --input pilot-power-input.json --output power-calculation.json` estimates a seed-block sample size from at least three real Pilot paired differences. The input freezes the test method, alternative, smallest relevant effect on the null-adjusted scale, familywise alpha, primary family size, target power, simulation seed, and resource-based maximum seed blocks. The calculator resamples centered empirical Pilot residuals under that effect, uses Holm's first-step Bonferroni threshold as a conservative per-hypothesis bound, and selects the first sample size whose Monte Carlo 95% lower bound reaches target power. It supports the registered paired t and paired sign-flip tests; the latter repeats Formal's exact test through 20 blocks and its frozen Monte Carlo permutation settings above 20. It records its own source hash and exact input hash; it does not invent Pilot data or choose the effect, task count, or resource cap.

`evotau-profile-cost --input pilot-cost-input.json --output cost-profile.json` creates a descriptive per-condition cost profile from per-episode budget snapshots. The version 1 input freezes a model-specific prompt/completion price schedule, currency, effective date and source digest; each episode carries explicit validity and verified-failure flags plus before/after provider snapshots. The report includes attempt/token mean and p95, valid rate, verified-failure yield, and price-schedule estimates. Missing token usage, unpriced/legacy model IDs, or cache-hit token ambiguity marks coverage incomplete; the priced subtotal excludes uncertain model subtotals and is labeled a lower bound. The CLI hashes the exact input and never overwrites an existing report. It makes no provider calls and does not fetch or select prices.

`evotau-formal-preflight --input formal-plan.json --output formal-preflight.json` checks the Formal design record: pilot artifact and power-calculation references, required primary contrasts for RQ1–RQ3, Holm adjustment, clean/H non-inferiority margins, disjoint E/V/H panels, sample-size seed schedule, equal condition budgets, required ablations, and blinded double-review calibration. With local artifacts, it verifies hashes, confirms each power input is frozen in the plan, re-derives its ordered paired differences from the cited Pilot report, and checks the result's hypothesis, Pilot/input/calculator hashes, test method, registered permutation settings, alternative, margin, family threshold, minimum relevant effect, planned sample size, and achieved lower power bound. It does not choose effects or margins, inspect the external registry URL, or imply that registration occurred; those decisions and evidence must come from a completed Pilot and registered plan.

`evotau-formal-analyze --plan formal-plan.json --rq1-report rq1-report.json --rq2-report rq2-report.json --rq3-report rq3-report.json --output formal-analysis.json` applies the eight frozen primary comparisons to complete descriptive run-level reports. Each report must be the analyzer's `{ "input_sha256": ..., "analysis": ... }` artifact; RQ2 analysis can be serialized from `RQ2RobustnessReport.to_dict()` with the source-input digest alongside it. The command verifies the plan's local artifact hashes, the registered seed/task/budget schedules and paired denominators, then runs the preregistered paired t or sign-flip test and Holm adjustment. The report records source artifact/input hashes, per-seed differences, raw and adjusted p-values, and registered permutation settings; it never overwrites an existing output. It fails closed on missing or incomplete runs. It does not verify that the external registry record exists, and computed p-values are not evidence that unrun study data exist.

`evotau.study_analysis.analyze_rq1_customer_advantage()` compares adaptive Customer search with the frozen-static and random-mutation controls. Each independent evolution-seed block must include all three conditions with the same frozen task panel, task/episode-seed schedule, and request-attempt cap. The report calculates verified unique `(task, signature)` yield, attributable-failure rates and denominators, and a paired percentile interval resampled only over independent seed blocks. Fewer than three independent blocks is reported as insufficient for the planned pilot comparison. The interval is descriptive; a formal claim still needs a pre-registered analysis plan and pilot-informed sample size. No study-run data is checked in, so this implements analysis logic without manufacturing research evidence. To analyze a version 2 JSON artifact, run `evotau-analyze-rq1 --input study-runs.json --output rq1-report.json`; the strict schema requires audited source and fresh-seed reproduction episodes for each verified failure, the report binds to the exact input-file SHA-256, and an existing report path is never overwritten.

RQ1 controls have explicit construction helpers in `evotau.baselines`: `StaticCustomerPortfolio` accepts only a researcher-frozen, hashed portfolio covering every level of the four MVP behavior fields, and its balanced `StaticCustomerSchedule` assigns each ordered task/seed pair before execution and validates resulting `EpisodeRecord`s. `propose_random_mutation_candidates()` uses the deterministic legal mutation operators without accepting failure evidence, so it cannot become failure-conditioned by accident. The package deliberately does not invent the actual static portfolio; freeze and review it with the study protocol before collecting Pilot runs.

The RQ2 one-shot Service control is implemented in `evotau.service_baselines`. Freeze the preregistered initial attack panel, S₀, and its generation-0 verified failures as an `InitialAttackEvidence` artifact, then wrap the normal `GatedServiceTransition` in `OneShotServiceTransition`. The wrapper forwards only that exact evidence set to the shared policy audit and paired gate, refuses missing or altered evidence, and keeps the resulting Service fixed in generation 1. Its explicit runtime provenance binds the frozen evidence into Phase 3 resume identity. This protocol does not collect the initial attack panel or choose its contents; real execution still needs that reviewed evidence and the frozen provider setup.

`evotau.service_analysis.analyze_service_repair_crossplay()` summarizes paired incumbent/candidate Service matrices for target, historical, clean, validation, or heldout panels. Cross-play cells retain native success, policy-violation, per-signature verified failure, repaired-signature recurrence, and invalid repeated-write counts with their audit coverage. The analysis reports gate acceptance, accepted-target failure-rate reduction, clean-user success/violation changes, repeated-write-rate changes when both matrices are fully audited, heldout success/failure changes, and historical recurrence/coverage, with gate, target-failure, and matrix hashes. It requires both matrices to use the same frozen prior-repair signature set, a fully audited native-user cell, and matching task, seed, and frozen Customer panels. `analyze_rq2_service_robustness()` groups the five panel reports by condition and independent evolution seed, validates fixed E/V/H partitions and budgets, and bootstraps adaptive-versus-one-shot paired effects at the seed-block level. Paired conditions must have matching task/seed schedules and request caps; missing denominators remain explicit. Use `evotau-analyze-rq2 --input rq2-runs.json --output rq2-report.json` for the strict version 2 JSON format: each seed includes `adaptive_coevolution` and `one_shot_repair` runs, the report binds both source runs by SHA-256, and the Formal analyzer checks the preregistered target-effect contrast against the one-shot baseline. The CLI writes an exact input SHA-256 wrapper and never overwrites an existing report. Percentile intervals are descriptive; Formal claims still require a preregistered inferential plan, calibrated audits, and real study data.

`evotau.native_runner.run_native_phase3` connects the controller to the pinned τ-bench `run_simulation` path without forking its runtime. It requires a complete Phase 0 result and adjacent manifest/simulation whose upstream pin, E task, source fingerprints, role models, seed, and budget record match the Phase 3 manifest. It records the Phase 0 result fingerprint into an immutable `run-context.json` and checkpoint, and carries Phase 0's provider attempts into the shared 1,800-attempt ceiling. Phase 0's one episode also counts toward the 23-episode limit. Live use needs a caller-supplied independent episode audit plus either a complete ServiceTransition or separate repair-proposal and independent repair-audit providers. `ServiceRepairInput` carries the verified target record, linked episode and native trajectory, pinned Retail policy text, same-signature history, selected Customer, and incumbent Service to both proposal and separate audit callbacks. Each episode audit must explicitly count invalid repeated writes. The built-in `GatedServiceTransition` runs fixed-seed paired target, historical, native-clean, and V-validation panels, checks S₀ clean-success anchors, and rejects incomplete gates. The two-generation ceiling permits at most one complete 10–11 episode Service gate after Customer panels; a second gate is skipped with an explicit inconclusive budget note. τ-bench's native reviewer alone cannot supply EvoTau's independent judgments. A pinned-runtime end-to-end test executes the actual τ-bench orchestrator, Retail tool, `run_simulation` evaluator, and full reviewer with a deterministic local completion stub; no provider call or research episode is made. On successful completion, the runner writes an immutable `phase3-result.json` index that binds the final shared budget and two generation decisions to the Phase 0 parent, checkpoint, per-episode records, telemetry, and native trajectories by SHA-256. Repeating an already completed run must reproduce that exact index; changed artifacts fail closed.

The equivalent command-line entry point is `evotau-phase3-run --config configs/phase3-mechanism.yaml --phase0-result PATH --tau2-data-dir PATH --provider-plugin MODULE:FACTORY`. The manifest must explicitly enable real-provider use and freeze all five Phase 3 model IDs/settings. The plugin factory receives the loaded config and frozen manifest, and returns `audit_provider` plus either `service_transition` or both `service_proposal_provider` and `service_repair_audit_provider`; `customer_proposal_provider` is optional because the manifest-bound LLM Evolver is the default. The factory must return callbacks without issuing requests. The CLI checks pinned data and the Phase 0 parent before loading the plugin. It fingerprints every Python source file in a provider package, each callback's defining source file, and the plugin specification into immutable `run-context.json`; a resumed run refuses changed provider code. Callback model requests must use τ-bench's `tau2.utils.llm_utils.generate` (or its dynamically resolved completion boundary) so retries are disabled and attempts enter the shared budget; direct SDK calls or a copied completion function reference bypass that guard and are unsupported. Independent audit callbacks return `IndependentEpisodeAudit`; τ-bench's native reviewer cannot substitute for this evidence. The command prints the immutable result path and budget summary. The CLI and callback contract are offline-tested; provider-backed Phase 0, full native Phase 3, 10–25 episode smoke, Pilot, and Formal remain unrun.

## Phase 4 Pilot execution scaffold

`evotau-pilot-preflight --config pilot.yaml --tau2-data-dir PATH --output preflight.json` checks the three-generation, multi-seed manifest and, when pinned τ-bench data is supplied, verifies exact task/split blob fingerprints, train E/V versus test H membership, eligibility, and entity disjointness. The task IDs still need an ex-ante semantic review for policy/tool compatibility and satisfiability; EvoTau does not choose a Pilot partition. No Pilot config is checked in, and the provider-enabled flag remains false by default.

`evotau-pilot-run --config frozen-pilot.yaml --tau2-data-dir PATH --provider-plugin MODULE:FACTORY` runs isolated per-seed checkpoints, a shared per-seed request budget, three Customer generations over multiple E tasks, final V followed by sealed H, and immutable seed/result indexes. The plugin factory's seed argument is a deterministic episode-seed base allocated to that block; the original evolution-seed label remains in the manifest and result. The base reserves a non-overlapping range for each block so paired conditions and independent seeds cannot accidentally reuse the same task/seed schedule. The current native Pilot executor supports `adaptive_coevolution` and `one_shot_repair`; the RQ1 `static_customer` and `random_mutation` schedule/proposal helpers and the RQ1/RQ2/RQ3 analyzers exist, but those control schedules are not yet wired into this Pilot CLI. The plugin constructs independent audit and Service callbacks without issuing requests; actual calls must use τ-bench's dynamically resolved completion boundary to enter the shared budget. The synthetic native orchestration test uses stub callbacks and makes no provider requests. A provider-backed Pilot, human attribution calibration, and Formal remain unrun.
