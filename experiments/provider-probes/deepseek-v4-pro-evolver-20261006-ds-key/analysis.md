# DeepSeek V4 Pro provider capability probe (Stage A)

**Stage A passed. No τ-bench episode, E/V/H panel run, or task evaluator was started.** The DeepSeek-group Keychain item is account `openai-api-key`; the previous GPT-group key failure is a separate provider group and does not represent this credential. No secret value is stored here.

The probe used InferAI `https://inferaiapi.com/v1` through the repository's `LLMAlternatingEvolvers` / `tau2.utils.llm_utils.generate` / LiteLLM Chat Completions path. Every dispatched call had `num_retries=0`. The first local harness validation error was not a provider call and is retained separately with `provider_request_dispatched=false`.

The small JSON request succeeded in 3.419 seconds, returned model `deepseek-v4-pro`, and parsed to the requested exact JSON. It included `reasoning_effort=high` and `extra_body.thinking.type=enabled`; the response contained a `reasoning_content` field (text omitted). Its caller-imposed `max_tokens=64` caused `finish_reason=length` after the JSON was already complete, so that request is not evidence about ample output capacity.

The first large-context call used the unmodified archived 20-task Service Evolver trajectories with an empty SkillMemory, replacing only the old `current_service_strategy` fields with `current_service_skill_memory={"skills":[]}` and its stable memory ID. Every trajectory was byte-for-byte preserved in canonical JSON, there were no `user_scenario` fields, and the context was 356,476 bytes (109,176 provider-reported prompt tokens). The first request included a caller-imposed 4,096 completion-token cap; InferAI returned no visible content after 61.647 seconds and τ-bench logged `finish_reason=length`. This was a bad probe output cap, not a 504 or context rejection. It is retained as a failed first attempt.

The corrected long-context request kept the exact same context and prompt, removed `max_tokens`, and still used one call with no retries. It completed in 73.423 seconds, returned model `deepseek-v4-pro`, ended with `finish_reason=stop`, and passed the production strict JSON / SkillMutation parser. The valid proposal was `NO_OP` for an empty SkillMemory. This output is provider-capability evidence only and was not applied to a checkpoint or run. Usage was 109,176 prompt tokens, 8,006 completion tokens, including 7,770 reasoning tokens. The provider returned reasoning metadata, but did not echo the requested effort level; therefore `reasoning_parameter_verified_by_provider=false` is recorded in the Stage B manifest.

Across the DeepSeek-group probe, three provider calls were dispatched (small, capped large, corrected large), with zero retries, zero observed 5xx responses, and zero client timeouts. The caller cap was removed for the successful large request. No system prompt reasoning text was persisted; artifacts record only its presence and character/token counts.

The Stage B config uses `openai/deepseek-v4-pro` as Evolver and retains DeepSeek V4 Flash for Customer, Service runtime, and Evaluator. It records the unverified provider checkpoint alias and the conservative reasoning verification flag. Before Stage C, the Retail task loader was also changed to stream task records and instantiate only requested task IDs: this is necessary because τ-bench's stock `get_tasks()` validates every record before filtering, which would transiently load sealed H records during E-only evolution. Tests and a direct E-only task-load preflight now verify that V/H task objects are not parsed or handed to the simulation.
